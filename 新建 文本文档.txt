# 项目开发任务书：高校师资/人才智能画像与辅助管理平台（B3）

## 一、你的角色

你是一名资深全栈工程师、系统架构师、数据工程师和 AI 应用开发工程师。请负责设计并实际开发一个可以运行、可以演示、具有真实业务逻辑的 Web 系统。

项目名称：高校师资/人才智能画像与辅助管理平台。

项目编号：B3。

项目定位：为高校学院、人事管理部门和研究生培养管理人员提供教师多维画像、人才结构分析、导师智能匹配、职称申报材料归集和青年人才引进辅助评估能力。

不要只输出技术建议、代码片段或静态原型。应当在当前工作目录中检查现有项目，直接创建或修改代码，运行项目、执行测试并持续修复问题。

## 二、项目目标

构建一个完整的高校师资人才智能管理系统，实现以下核心业务：

1. 教师基础档案与多维画像。
2. 教师科研、教学、社会服务成果的关联与统计。
3. 学院和学科层面的人才盘点与结构分析。
4. 导师与学生的智能匹配及可解释推荐。
5. 教师职称申报材料的自动归集、缺项检查和核验。
6. 青年人才引进岗位与候选人的智能匹配及辅助评估。
7. Excel/CSV 数据导入、数据质量检查、结果导出和系统管理。

必须优先实现可运行的 MVP，再逐步完善 AI 能力。禁止用纯静态页面、硬编码统计数据或假按钮冒充完整功能。

优先使用以下技术：

前端：

- TypeScript

- Pinia（需要共享状态时使用）

后端：
- Python

数据存储：

- 使用 Pandas 处理 Excel/CSV。
- 文件上传需进行类型、大小和内容校验。

AI 能力：
- 设计独立的 LLM 服务接口层，支持通过环境变量配置模型服务商、API Key、API Base URL 和模型名称。
- 需要文本语义匹配时使用 Embedding 服务。
- 对 AI 调用设置超时、异常处理和必要的重试机制。
- 没有配置 API Key 时，核心 CRUD、统计、规则评分和材料检查仍然能够运行。
- 不允许把 API Key 写入前端代码或提交到 Git。
- 默认不得将真实教师个人信息发送至外部模型；AI 服务必须可配置，并提供脱敏或本地处理方案。

如果当前目录已有项目，先检查已有代码和依赖，尽可能沿用合理的现有技术栈，不要未经检查就推倒重建。

## 四、核心业务模块

### 模块 1：教师档案管理

建立教师档案，至少包含：

- 教师唯一编号。
- 姓名。
- 学院、院系、学科。
- 学历、职称、职务。
- 入职时间、研究方向。
- 个人简介、专业技能、研究关键词。
- 教师状态。
- 数据来源和最后更新时间。

提供新增、编辑、详情、删除或停用、关键词搜索、多条件筛选和分页。

数据变更时应校验必填字段、唯一编号及关联关系。对已关联科研成果的教师执行删除操作时，应防止产生孤立记录。

### 模块 2：科研、教学和社会服务成果管理

建立关联业务实体：

1. 科研论文及其他研究成果。
2. 科研项目、经费、负责人和项目参与关系。
3. 教学课程、教学工作量、教学成果。
4. 获奖、学术任职、社会服务等记录。

每条成果记录应有独立 ID、类型、名称、时间、关联教师和数据来源。

实现：
- 成果新增、编辑、查询。
- Excel/CSV 导入。
- 必填字段校验和错误明细下载。
- 重复成果检测。
- 教师与成果的关联查询。
- 按时间范围、学院、学科和成果类型进行统计。

统计必须从数据库实际数据计算，不得将演示数字写死在前端。

### 模块 3：教师多维智能画像

建设教师画像详情页，至少包含：

- 基本信息和研究方向。
- 科研成果数量及年度趋势。
- 项目参与情况。
- 教学工作量和教学成果。
- 社会服务与学术任职。
- 能力标签与研究关键词。
- 数据完整度和最近更新时间。
- 画像摘要和发展建议。

科研、教学和服务等维度优先展示客观统计指标及其计算口径。

如果引入综合评分，必须显示各指标、权重、数据来源和缺失情况。不要将缺失数据自动视为零分，也不要在数据不足时生成确定性评价。

LLM 只负责基于已有事实生成摘要、归纳研究方向和辅助提出发展建议。不得虚构论文、项目、奖项或任职经历。重要结论应关联具体数据记录。

### 模块 4：人才盘点与管理驾驶舱

实现管理驾驶舱，展示：

- 教师总人数。
- 学院、学科和职称分布。
- 学历及年龄梯队分布（仅在数据合规且有真实字段时展示）。
- 科研成果数量和年度趋势。
- 项目参与及教学工作量统计。
- 人才结构和研究方向分布。
- 数据缺失、重复和待核验记录。
- 可筛选的统计图表。

提供学院、学科、职称、时间范围等筛选条件。

实现人才盘点报告生成和导出。报告中的所有数字必须能从数据库查询复现。

对于“人才缺口”等分析，应由管理员配置的岗位需求、学科规划或明确指标作为依据，不得仅凭模型生成结论。

### 模块 5：导师—学生智能匹配

建立学生需求和导师匹配业务。

学生需求至少包含：
- 专业和学科背景。
- 研究兴趣及关键词。
- 期望研究方向。
- 培养需求及其他明确条件。

导师信息应包含：
- 研究方向和具体研究主题。
- 相关成果。
- 指导资格。
- 招生状态。
- 可指导容量。

匹配逻辑：

第一步：按照资格、招生状态、指导容量等硬性条件过滤候选导师。

第二步：计算研究方向、研究主题、培养需求等维度的匹配分数。

第三步：将候选导师排序，输出匹配总分、分项得分、匹配理由和不匹配因素。

第四步：支持调整评分权重、查看候选详情和记录人工确认结果。

初始权重可以使用研究方向相似度 40%、具体主题匹配度 25%、培养需求匹配度 20%、指导容量适配度 15%，但应当允许管理员配置，并在界面展示权重。

没有配置 Embedding 服务时，使用关键词匹配或 TF-IDF 等可运行的备用算法。

匹配解释必须对应真实数据，不得仅由 LLM 编造理由。总分不能抵消硬性资格条件不满足的问题。

### 模块 6：职称申报材料归集

建设职称申报辅助中心。

功能包括：
- 申报批次和职称类型配置。
- 申报要求和材料清单模板管理。
- 教师已有论文、项目、获奖、教学成果等记录自动汇总。
- 已有材料与申报要求关联。
- 缺失项、重复项、信息冲突和待核验项识别。
- 人工确认、补充、驳回和备注。
- 申报材料清单及汇总报告导出。

不同职称的申报条件必须支持配置，不能把示例规则当作所有高校的统一政策。

如支持 PDF、Word 等附件，需将文件解析设计为独立服务，并记录解析失败和待人工确认状态。

材料检查不能声称已经验证成果真伪；只能对已有数据和可访问证据进行一致性、完整性和重复性检查。

### 模块 7：青年人才引进辅助评估

建设岗位与候选人匹配中心。

岗位信息包括：
- 岗位名称。
- 所属学院、学科和研究方向。
- 必要资格。
- 研究主题和岗位要求。
- 可配置的评价维度及权重。

候选人信息包括：
- 基本专业背景。
- 研究方向。
- 科研成果和项目经历。
- 教学及其他岗位相关经历。
- 资料来源和待核验字段。

实现：
- 岗位创建、编辑和管理。
- 候选人档案导入。
- 岗位要求与候选人经历匹配。
- 必要条件校验。
- 候选人排序和对比。
- 各维度评分、推荐理由、差距和证据来源展示。
- 人工评审意见、状态和操作记录。

评价规则必须可解释、可配置，并避免使用无关或不适当的个人属性作为评价依据。

系统只能提供辅助建议，不能自动作出录用或淘汰决定。

### 模块 8：数据管理、权限与审计

实现：
- Excel/CSV 导入和模板下载。
- 数据校验结果及失败原因。
- 导入批次和数据来源记录。
- 基础用户登录。
- 管理员、业务人员、只读用户等基本角色权限。
- 敏感数据访问控制。
- 重要操作审计日志。
- 环境变量配置。
- 健康检查接口和错误日志。

教师个人信息、联系方式及未公开材料不得无差别展示。按照最小权限原则设计访问控制。

## 五、数据模型设计要求

请至少考虑以下实体：

- User：用户及角色。
- Teacher：教师档案。
- ResearchOutput：科研成果。
- ResearchProject：科研项目。
- ProjectMember：项目参与关系。
- TeachingRecord：教学记录。
- ServiceRecord：社会服务记录。
- StudentProfile：学生需求档案。
- AdvisorMatchTask：导师匹配任务。
- AdvisorMatchResult：匹配结果。
- PromotionBatch：职称申报批次。
- PromotionRequirement：申报要求。
- PromotionMaterial：申报材料。
- JobPosition：人才招聘岗位。
- CandidateProfile：候选人档案。
- CandidateEvaluation：岗位匹配与评审记录。
- ImportBatch：数据导入批次。
- AuditLog：操作审计日志。

根据实际关系设计主键、外键、索引、唯一约束和时间字段。

避免将所有业务数据塞进一个大 JSON 字段。对需要筛选、统计和关联的数据建立规范化表结构。

## 六、前端页面要求

使用统一的高校管理平台视觉风格，布局清晰、适配桌面端。

左侧导航栏：
1. 人才驾驶舱。
2. 教师档案。
3. 智能画像。
4. 人才盘点。
5. 导师匹配。
6. 职称申报。
7. 人才引进。
8. 数据管理。
9. 系统设置。

主要页面应包含：
- 清晰的页面标题和操作按钮。
- 搜索、筛选、分页和排序。
- 加载状态、空数据状态和错误提示。
- 表单验证和操作反馈。
- 详情页与业务数据关联。
- 合理的图表、表格、统计卡片。
- 必要的二次确认。
- 真实的数据查询与保存。

禁止使用无功能的按钮、固定写死的推荐结果、纯装饰图表或不与后端交互的假表单。

## 七、后端 API 要求

按 REST 风格设计接口，至少覆盖：

- 教师档案 CRUD。
- 科研成果和项目 CRUD。
- 教学与服务记录 CRUD。
- Excel/CSV 导入及导入结果查询。
- 教师画像和人才统计查询。
- 人才盘点报告生成。
- 导师匹配任务创建、执行和结果查询。
- 职称申报批次、要求和材料管理。
- 招聘岗位、候选人及匹配评估。
- 用户认证和权限检查。
- 审计日志查询。
- 服务健康检查。

使用 Pydantic 校验输入输出，统一处理业务异常，生成 OpenAPI 文档。

所有重要查询和修改都应检查用户权限。对于长耗时 AI 操作，应设计明确的运行状态和失败反馈。

## 八、模拟数据与演示

为了让系统在没有真实高校数据的情况下可以演示，生成合理且互相一致的模拟数据。

建议至少准备：
- 100 名教师。
- 多个学院和学科。
- 多年科研成果和项目记录。
- 教学及社会服务数据。
- 20 名学生需求档案。
- 多个导师招生状态和指导容量。
- 5 个以上招聘岗位。
- 多名候选人档案。
- 不同完成状态的职称申报批次。

模拟数据应有明确标识，不得冒充真实数据。

确保教师 ID、成果关联、项目关系和统计结果一致。

提供一键初始化或种子数据脚本，并确保重复执行不会无控制地生成重复记录。

## 九、测试与质量要求

必须覆盖以下场景：

1. 后端能够启动，健康检查正常。
2. 前端能够启动，页面可访问。
3. 教师档案能够新增、修改、查询。
4. Excel/CSV 导入能识别错误字段、缺失值和重复记录。
5. 教师画像统计与数据库中的实际数据一致。
6. 人才盘点筛选条件生效。
7. 导师匹配能够返回真实计算的分数和解释。
8. 不符合硬性条件的导师不会因为总分高而进入有效推荐。
9. 职称材料能够正确标记缺项和待核验项。
10. 人才岗位匹配能够展示各维度分数和证据。
11. 没有 API Key 时，基础功能和规则算法仍然可以使用。
12. 不同角色不能访问未授权的数据和接口。
13. 数据库中的数据重新启动后仍然存在。
14. 所有导出文件能够正常打开。
15. 核心业务异常具有可理解的错误提示。

为关键算法、API 和数据处理编写自动化测试。运行测试后修复发现的问题，并说明仍未通过的项目。

## 十、开发执行方式

请按照以下顺序实际执行：

第一阶段：检查当前目录、现有代码、依赖、运行环境和项目状态。列出发现的问题和建议架构。

第二阶段：编写简明的实施计划、目录结构、数据库模型和核心业务流程。随后立即开始编码，不要只停留在计划。

第三阶段：完成前后端骨架、数据库、教师档案 CRUD 和模拟数据初始化，先验证端到端链路。

第四阶段：实现教师画像、人才驾驶舱、成果管理和 Excel 导入。

第五阶段：实现导师匹配、职称申报材料归集和人才引进评估。

第六阶段：完善权限、错误处理、测试、报告导出和演示数据。

第七阶段：实际启动前后端，运行自动化测试，检查页面和 API，修复可复现的问题。

每完成一个阶段，都应总结：
- 已完成的功能。
- 新增或修改的文件。
- 运行方式。
- 测试结果。
- 遗留问题。
- 下一阶段计划。

如果存在不确定的业务规则，请先使用可配置规则和合理的模拟数据实现，并将假设写入文档；不要凭空宣称这些规则来自真实高校制度。

遇到无法安装的依赖或不可用的外部服务时，优先采用轻量、可本地运行的替代方案，不要因此停止整个项目。
